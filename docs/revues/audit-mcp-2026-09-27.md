## 1. Transport

### Versions (lockfile)

- `@modelcontextprotocol/server@2.0.0` (`package.json:58`, `pnpm-lock.yaml:872`),
  qui dépend de `@modelcontextprotocol/core@2.0.0` et `zod@4.3.6`.
  `@modelcontextprotocol/sdk@1.29.0` figure aussi au lockfile, mais comme
  dépendance de `shadcn` (`pnpm-lock.yaml:7907`) : le serveur ne l'utilise pas.
- Point d'entrée : `createMcpHandler` (SDK). Il sert la révision **2026-07-28**
  (`FIRST_MODERN_PROTOCOL_VERSION = "2026-07-28"`, `dist/src-CX2iR2pK.mjs:544`)
  et, par défaut (`legacy: 'stateless'`), l'ère 2025 en **Streamable HTTP sans
  état** : un serveur neuf par POST, `sessionIdGenerator: undefined`, GET et
  DELETE → `405 Method not allowed` (`dist/index.mjs:966-968`).
- Transport : **Streamable HTTP**, sans session. Pas de SSE « HTTP+SSE 2024 ».

### T1 — pourquoi une requête reste ouverte 300 s (grave, corrigé)

**Preuve, production** (journal Vercel, 7 jours, route `/api/mcp/[cle]`) :
143 × « Vercel Runtime Timeout Error: Task timed out after 300 seconds »,
premier le 2026-08-16T11:22:51Z, dernier le 2026-09-27T12:55:56Z. Aujourd'hui :
POST à 12:35:50, 12:39:51, 12:43:52, 12:47:53, 12:51:54, 12:55:56 — **statut 200**,
un toutes les 4 min 01 s. Un 200 qui dure 300 s est un flux ouvert, pas un
calcul lent.

**Ce que le SDK fait.** Trois voies seulement produisent un flux :

1. POST 2025 : SSE par défaut, mais `stream.cleanup()` ferme dès que toutes les
   réponses de la requête sont parties (`dist/index.mjs`, `send`, fin de
   classe `WebStandardStreamableHTTPServerTransport`). Se termine.
2. POST 2026-07-28 ordinaire : JSON, ou SSE « upgradé » qui se ferme sur la
   réponse (`finalizeStream`, `PerRequestHTTPServerTransport`). Se termine.
3. **POST `subscriptions/listen`** (2026-07-28) : `createListenRouter.serve`
   (`dist/mcp-DXXb3Vv3.mjs:219-310`) écrit l'accusé de réception, arme un
   `keepalive` toutes les 15 s (`DEFAULT_SSE_KEEP_ALIVE_MS = 15e3`, l. 62) et
   **ne ferme que sur abandon du client ou `handler.close()`**. Même quand le
   filtre accordé est vide.

**Ce que dit la spécification** (lue le 2026-09-27) :
- *Streamable HTTP* (2026-07-28) : « Long-lived notification streams are
  obtained by sending a `subscriptions/listen` request. The server's response
  is itself an SSE stream that stays open […] Until the client or server
  closes the stream. » Et : « The final JSON-RPC response SHOULD terminate the
  stream. » La révision retire le flux GET et les sessions ; à un client
  ancien, GET/DELETE « SHOULD » recevoir `405`.
- *Subscriptions* § Cancellation : un abonnement finit quand « the server
  tears it down […] it SHOULD send a successful `subscriptions/listen`
  response to signal a graceful end […] then close the stream » ; l'accusé
  « MUST » être le premier message ; « a transport that closes without it
  indicates an unexpected disconnect, which the client MAY treat as a trigger
  to reconnect ».
- *Tools* § Capabilities : « `listChanged` indicates whether the server will
  emit notifications when the list of available tools changes. »

**Mesure locale** (appel direct du gestionnaire de route, `transport-http.test.ts`) :
avant correction, `subscriptions/listen` **encore ouvert à 35 004 ms** quand le
test l'a coupé (`[mesure] subscriptions/listen ouverte 35004 ms`) ; il l'aurait
été jusqu'à l'abandon du client. `initialize` et `tools/call`, 2025 comme
2026-07-28 : fermés dès la réponse (0 à 11 ms, prisma simulé). Après
correction : `subscriptions/listen` fermé immédiatement, avec accusé puis
réponse `complete`.

**Cause.** Le client (le connecteur Claude.ai, dont le rythme de 4 min
correspond) ouvre un `listen` parce que le serveur annonce `listChanged: true`
(T2) ; le SDK tient ce flux indéfiniment ; sur Vercel, « indéfiniment » = le
plafond de 300 s, instance et connexion base comprises.

**Correctif** (`src/lib/mcp/http.ts`) :
- l. 98 : `capabilities: { tools: { listChanged: false } }` ;
- l. 179-259 `terminerEcoute` : l'accusé du SDK est relayé (il a validé
  version, en-têtes et filtre), suivi de la réponse `{"resultType":"complete"}`
  portant `subscriptionId` et `serverInfo`, puis fermeture et annulation du
  flux SDK (désabonnement, arrêt du minuteur) ;
- l. 295 et 310 : appliqué quand `Mcp-Method: subscriptions/listen` — en-tête
  exigé et confronté au corps par le SDK (`validateStandardRequestHeaders`,
  `dist/src-CX2iR2pK.mjs:5041`), donc non déguisable.

**Risque résiduel, à regarder après déploiement** : un client qui rouvrirait
un `listen` aussitôt après une fin gracieuse. La spécification le lui
déconseille (la fin est « voulue ») ; si le journal montre des POST en rafale,
la réponse est un `404 -32601` sur `subscriptions/listen`, pas un délai.

## 2. Efficience

- **Un client Prisma par invocation ?** Non : `prismaMcp` est au niveau module
  (`src/lib/mcp/prisma.ts:18`), un par instance. La connexion est ouverte au
  premier appel et vit avec l'instance ; en mode transaction
  (`connection_limit=1`), c'est la bonne forme. Ce qui saturait le pool en
  mode session, c'était des instances maintenues vivantes 300 s par T1.
- **E1 (faible).** `@/lib/calendrier/fraicheur` importe `@/lib/prisma`
  (`fraicheur.ts:65`) : le bundle MCP instancie aussi le client de
  l'application. Il ne se connecte pas tant qu'on ne l'interroge pas (le MCP
  n'utilise que `fraicheurDepuisRepere`, pure), mais c'est une deuxième pool
  potentielle. Recommandation : sortir `fraicheurDepuisRepere` dans un module
  sans import Prisma.
- **N+1 ?** Non. Chaque outil fait une requête Prisma avec relations
  imbriquées (`queries.ts` : `listerVerifications`, `listerEquipements`,
  `getEtatDuerp`) — Prisma les résout en un nombre fixe de requêtes, pas une
  par ligne.
- **E2 (faible).** Par appel : `getNomEtablissement` (1), plus pour
  `verifications`/`plan_actions` `getFraicheurCalendrier` (1 + un `count`),
  plus le contenu. Deux lectures du même établissement. Fusionnable ; gain
  marginal.
- **Cache.** Aucun possible sans risque : données par établissement, lues en
  direct, portée dépendant du porteur. `dynamic = "force-dynamic"` est juste.
- **E3 (faible).** `middleware.ts:20` couvre `/api/mcp` ; `updateSession`
  crée un client Supabase et appelle `getUser()` avant de laisser passer
  (`src/lib/supabase/middleware.ts:80`, `"/api/mcp"` l. 32). Sans cookie, pas
  d'aller-retour réseau, mais un travail inutile par requête. Recommandation :
  exclure `/api/mcp` et `/.well-known/` du `matcher`.
- **E4 (faible).** Réponses non bornées (un calendrier de plusieurs centaines
  de lignes part en un bloc). Recommandation : pagination ou plafond annoncé.

## 3. Sécurité

### S1 — la clé dans l'URL, dans le journal (grave, décision)

**Preuve** : chaque ligne du journal Vercel de la route porte le chemin
complet, clé comprise (relevé de ce jour, 9 lignes entre 12:35:47 et
12:55:56). Le code n'y est pour rien — c'est la ligne de requête que la
plateforme journalise — et **aucun correctif de code ne peut l'empêcher tant
que la clé est dans le chemin**. La clé est aussi exposée à tout outil qui
lit ce journal (y compris les sessions d'agent), aux historiques, aux
copier-coller. `acces-http.ts:10-16` l'assumait « sur des données fictives » ;
il faut vérifier que c'est toujours le cas de l'établissement servi.

Le connecteur Claude.ai n'offre pas de champ d'en-tête (`acces-http.ts:3-8`) :
passer la clé en `Authorization` casserait ce connecteur. **Proposition** :
1. **Maintenant** : faire tourner `MCP_CLE` (elle est au journal depuis le
   2026-08-16) et recoller l'URL dans le connecteur — coupure du connecteur le
   temps de la mise à jour.
2. **Ensuite** : basculer le connecteur sur `/api/mcp` (OAuth, ADR-013, déjà
   en production) — plus aucun secret dans l'URL (la spécification :
   « Access tokens MUST NOT be included in the URI query string ») — puis
   retirer la route `[cle]`.
3. Optionnel, pour les clients qui savent poser un en-tête (Claude Code
   `--header`) : accepter la clé en `Authorization: Bearer` sur `/api/mcp`
   en plus d'OAuth. C'est un changement de mode d'authentification : **non
   fait**.

### S2 — rotation (moyen, décision)

Une seule variable `MCP_CLE` (`acces-http.ts:50`) : tourner = couper. Une
`MCP_CLE_PRECEDENTE` acceptée pendant une fenêtre permettrait la rotation
sans coupure. Non fait (change ce qu'un client peut présenter).

### S3 — OAuth : audience (moyen, décision)

`creerVerificateurSupabase` (`acces-oauth-deps.ts:48`) appelle
`getClaims(jeton)` : signature et expiration, **pas l'audience**. Tout jeton
d'accès Supabase du projet est accepté — y compris la session web de
l'utilisateur ou un jeton émis pour un autre client. La portée reste bornée
aux établissements de SON entreprise (`chercherEtablissementDeUtilisateur`,
l. 79-95), donc pas de fuite entre locataires ; mais la spécification
(Authorization § Token Handling) : « MCP servers MUST validate that access
tokens were issued specifically for them as the intended audience ». Suppose
un `aud` propre à la ressource côté serveur d'autorisation Supabase : décision
de configuration.

### S4 — limitation de débit (moyen, décision)

Aucune. Clé de ≥ 32 caractères (~192 bits, `acces-http.ts:27`) : pas de
balayage réaliste ; mais un porteur de clé (ou de jeton) peut enchaîner les
appels, chacun des lectures base. La spécification (*Tools* § Security) :
« Servers MUST […] Rate limit tool invocations ». Recommandation : règle de
limitation Vercel WAF sur `/api/mcp*` (écriture Vercel : non faite).

### S5 — établissement introuvable (moyen, corrigé)

`MCP_ETABLISSEMENT_ID` est lu au chargement (`acces-http.ts:51`), jamais
confronté à la base. Si l'établissement a été supprimé — **le code ne permet
pas de le constater, seule la base le dirait** — chaque appel d'outil faisait
une lecture (`getNomEtablissement`) et rendait un texte ordinaire : rien ne le
distinguait d'une réponse. Pas de boucle dans le code : la seule répétition
observée est T1, indépendante de l'identifiant.
Correctif : `ErreurOutilMcp` (`tools.ts`), levée l. 652 ; le transport la rend
en `isError: true` avec son message (`http.ts:124`), une ligne de journal
sans trace ; même contrat en stdio (`scripts/mcp-server.ts`). Une lecture,
aucune autre (test).

### S6, S7 — validation des entrées (faibles, corrigés)

- Les schémas zod n'avaient pas d'`etablissementId` (bien), mais un argument
  inconnu était **retiré en silence**. Désormais `.strict()` (`tools.ts:296`,
  et les deux schémas à filtres) : refusé, et le schéma annoncé porte
  `additionalProperties: false` — la forme recommandée par la spécification
  pour un outil sans paramètre.
- `recherche` bornée à 200 caractères (`tools.ts:541`). Les nombres l'étaient
  déjà (`criticiteMin` 0-100, `horizonJours` 1-3650).

### S8 — Host / Origin (faible, recommandation)

Gardes posées avant tout (`http.ts:280`) : `Host` hors liste → 403, `Origin`
présente et hors liste → 403 (exigence « MUST » de la spécification, § Security
& Endpoint). Deux réserves : `localhost` et `127.0.0.1` sont toujours dans la
liste, production comprise (`hotes.ts:33`) ; et le SDK compare le **nom
d'hôte** de l'Origin, pas schéma ni port (`validateOriginHeader`,
`dist/index.mjs:1680`). Portée pratique faible (clé ou jeton requis, pas
d'en-têtes CORS), mais réservez la boucle locale au développement.

### S9 — comparaison à temps constant (conforme)

`clesEgales` (`acces-http.ts:87-91`) : SHA-256 des deux côtés puis
`timingSafeEqual` — longueur fixe, pas de court-circuit.

### S10 — tenancy, erreurs, journaux (conforme)

- Portée : établie par la requête avant tout serveur (`http.ts`, `servir`) ;
  jamais un argument d'outil ; toute requête de `queries.ts` filtre par
  `etablissementId` reçu du contexte. OAuth : `?etablissement=` n'est accepté
  que s'il figure parmi ceux du porteur (`acces-oauth.ts`,
  `resoudreScopeDepuisJeton`).
- Erreurs : message générique au client, trace au journal seulement
  (`http.ts`, bloc `catch`) ; la réponse « choix requis » ne liste que les
  établissements du porteur.
- Journaux applicatifs : aucune clé, aucun jeton. L'identifiant
  d'établissement peut figurer dans un message d'erreur Prisma — non secret.
  Le SDK n'a pas d'`onerror` branché : ses rejets (en-têtes, version) ne sont
  pas journalisés — à brancher, sans le corps de requête.

## 4. Conformité produit

- **Consigne** (`tools.ts:73-84`) : « Rojer calcule, il n'avise pas » ; interdit
  « conforme », « en infraction », « opposable » ; n'autorise que les
  références rendues par un outil ; exige de signaler l'analyse comme venant
  du modèle. Conforme.
- **Descriptions** : factuelles. `etat_duerp` cite « art. R. 4121-2,
  applicable à partir de 11 salariés » (l. 316) — seul outil qui cite un
  article, ce que la consigne dit (l. 78). `verifications` distingue les
  « engagements d'assurance, marqués comme tels ». Aucune qualification
  juridique relevée.
- **Écart à vérifier.** Les instructions que le connecteur Rojer présente
  dans cette session disent « Les outils rendent des faits […] et les
  articles qui fondent une obligation » ; le code à `42c0390` dit « Seul
  l'état du DUERP cite des articles ; les autres outils n'en rendent aucun ».
  Soit le client a gardé la consigne de sa première connexion, soit le
  déploiement servi est antérieur. À vérifier en reconnectant le connecteur
  après déploiement.
